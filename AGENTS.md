# AGENTS.md

`scry` is a terminal task manager with a PostgreSQL backend: a clap CLI. Rust edition 2024. It is a Cargo workspace: the root `scry` binary and `crates/scry-core` (domain types and the `Store` trait). The tests are unit tests that need no database; `just cargo-test` (alias `just test`) runs them (`cargo test --workspace`).

## Tooling prerequisites

- The standard workflow uses `just` and sqlx-cli (`cargo install just sqlx-cli`). The `sqlx-prepare*` and `run-postgres` targets need sqlx-cli; the Postgres targets also need Docker, since they start and stop the Postgres defined in `compose.yaml`, which runs the app together with its own `postgres:18` service.
- `just run` (the `run-docker` alias) builds and starts the whole Docker stack, app plus database, so no host Postgres is needed; `just view-logs` tails the app container. `just run-local` builds the release binary and runs the REST server on the host against that same Postgres with `--config scry.dev.toml --secrets scry.dev-secrets.toml`, and `just run-postgres` only starts Postgres and applies migrations.
- `just pg-down` keeps the data volume and `just pg-reset` wipes it; `pg-reset` and `clean` take the whole stack down, and `clean` also runs `cargo clean`.
- rust-analyzer is configured to run `cargo clippy` as its check command (`.vscode/settings.json`), and `just cargo-clippy` (alias `just clippy`) is `cargo clippy --workspace -- -D warnings`. Keep clippy clean at `-D warnings`; CI runs it through `just validate` (`.github/workflows/ci.yml`), so `just validate` is your local gate: `cargo-test` -> `cargo-check` -> `cargo-clippy`.

## sqlx compile-time database (the #1 gotcha)

All SQL lives in `sqlx::query!`/`query_as!` macros in `src/store/postgres.rs`, and is resolved at compile time against the committed offline cache in `.sqlx/`.

- `.env` (committed) sets only `SQLX_OFFLINE=true`. sqlx reads `.env` at compile time, so ordinary `cargo build`/`check`/`test`/`clippy` resolve queries from `.sqlx/` and do **not** need a live database. A fresh clone therefore compiles without any database.
- Regenerating the cache is what needs a database. `just run-postgres` starts the dev Postgres and applies the migrations, and `just sqlx-prepare` runs `sqlx-prepare-postgres`, which brings up the dev Postgres (`pg-up`), prepares against it, and tears it down.
- After editing SQL in a `query!` macro or adding a migration, run `just sqlx-prepare`. Changing a query changes its hash, so a stale `.sqlx/*.json` breaks the build. Commit the migration and the regenerated cache together.
- `just sqlx-prepare-check` verifies the cache is current, using the dev Postgres as well; CI runs it. Release CI (`.github/workflows/release.yml`) builds with `SQLX_OFFLINE=true` against the committed cache.
- The runtime database is **not** the compile DB. The app never reads `.env`; it takes `database_url` only from `scry.toml` or `scry.secret.toml` (or the files named by `--config` / `--secrets`), with no environment-variable override and no local-file fallback — a missing URL is a startup configuration error, and only `postgres://` / `postgresql://` URLs are accepted. `cargo run` therefore talks to whichever database the resolved config points at, so point `database_url` at a scratch database when you do not want to touch real user data. The backend is built with sqlx's `tls-rustls` feature (in the root `Cargo.toml`), so URLs whose `sslmode` requires TLS connect correctly; removing that feature breaks them with a "built without TLS support" error.

## Migrations

- `migrations/` holds the reversible `20261031164943_init` pair, which creates the sections/lifecycle schema with native uuid ids and `TEXT COLLATE "C"` positions from scratch and seeds the built-in default project with a fixed UUID, plus the `20261101062730_sync_state` pair that adds the sync storage tables (`applied_operations`, `changes`, `entity_tombstones`). There is no legacy migration path and no data migration from earlier builds: the init migration is applied from scratch, so a database created before the UUID rewrite or before the position conversion must be recreated or migrated manually. The backup format is version 1 and any other version is rejected on import; there is no upgrade path. Add future migrations with `sqlx migrate add -r <name>`, filling in both files.
- Migrations are embedded (`sqlx::migrate!("./migrations")` in `src/store/postgres.rs`) and auto-run on **every app startup**. Databases created before the UUID rewrite or position conversion must be recreated; from this point on, new migrations must be additive/backward-compatible.
- The root crate has a `build.rs` that reruns when `migrations/` changes, so new migrations trigger a rebuild automatically.

## Architecture

- `src/main.rs` — clap command definitions and dispatch. Client commands go to `src/client/`; `serve` is the only database-backed path; `docs` and `skill` are local. With no subcommand it prints the top-level help.
- `src/client.rs` and `src/client/commands/**` — the HTTP client. `Client` (`src/client/http.rs`) builds URLs with `reqwest::Url`, sends the bearer token and `Time-Zone`, and maps server error documents into `AppError::Remote`. Each command has its own file, and `project_by_name`/`section_by_name` resolve names through the API. The client never opens the database.
- `src/output.rs` — shared `print_json`, `section_label`, and `task_line` rendering used by the client and the few local commands.
- `src/client_state.rs` — the client-local active project in `state.toml`; `set_active` persists a verified project name, and `project_by_name` falls back to `default` when it is stale.
- `src/service.rs` — `ProjectService` owns the store and is the only write path. It is the operations layer: it resolves section names to ids (exact match; an absent name fails), resolves task and note handles to UUIDs (failing on ambiguity with longer candidates), creates sections only when explicitly asked (`--new-section` or `section add`), merges sections by moving their tasks one at a time (not atomic), generates lexicographic position keys for new tasks and sections (new rows append), and mutates tasks by reading the row, changing fields, and writing it back through `Store::update_task` — so concurrent edits to different fields are last-write-wins. Reordering is not exposed: task moves always append, and sections cannot be reordered. Projects and sections remain name-based; tasks and notes accept id handles. Every server mutation (REST handlers, import) goes through it; reads may use `Store` directly. The REST `ScryState` holds the service, and the client reaches it over HTTP.
- `src/server/` — the REST router and one handler per endpoint. Detailed responses use `TaskDetails` (flattened task plus optional `notes` and `handle`) and the project detail response (flattened project plus `sections` and `tasks`).
- `crates/scry-core/src/ids.rs` — UUID id aliases (`ProjectId`, `SectionId`, `TaskId`, `NoteId` are `Uuid`) and the short-handle utilities (`Handle` parsing and range bounds, `shortest_handle`/`shortest_handles`). Rust generates every id: v4 for new entities and v5 for template sections, derived from the project UUID plus the section name; the database has no id defaults.
- `crates/scry-core/src/store.rs` — `Store` async trait declaring every DB operation. One implementor: `PostgresStore` (`src/store/postgres.rs`). All `query!` calls live there. Postgres stores ids as native `uuid` columns; task and note handles resolve with a padded `BETWEEN` range query over all rows (closed tasks included, across projects), while projects and sections stay name-based. It covers task CRUD plus a single `update_task` that writes the whole row; section CRUD plus `delete_section` (tasks fall back to No section); there is no section reorder operation; note and project CRUD; the project document snapshot read used by the snapshot endpoint and export; and import. Add new persistence via the trait plus the implementor.
- `crates/scry-core/src/models.rs` — domain types (`Task`, `Project`, `Section`, `Lifecycle`, `CloseReason`, `Priority`, …). A task has a nullable `section_id`, a `Position` string key, and a `lifecycle` of `Open` or `Closed { closed_at, reason }`. Positions use the default Rocicorp fractional-index format and sort lexicographically; every ordering breaks ties by `(position, id)`. `TaskSortingMode::Created` sorts by `(created_at, id)`, with `id` kept as a CLI alias for compatibility. `ProjectSnapshot` is the canonical project document — the project's own fields flattened into the object's top level alongside `sections`, `tasks`, and `notes` — returned by `GET /projects/{id}/snapshot` and used as each backup entry. `crates/scry-core/src/backup.rs` defines the backup/import envelope (`version`, `app_version`, `projects: Vec<ProjectSnapshot>`); the format is version 1 and any other version is rejected on import. `src/config.rs` handles config, server URL, and DB URL resolution, and `src/skill.rs` implements the embedded Agent Skill command.
- `crates/scry-core/src/position.rs` — the vendored default-format Rocicorp fractional-index algorithm (CC0), plus the `Position` newtype, validation, `key_between`, and `n_keys_between`. Keys look like `a0`, `a1V`, and `Zz`. `PostgresStore` stores them as `TEXT COLLATE "C"` so database and Rust ordering agree byte-for-byte.
- Row->model mapping is hand-rolled per query via the `*_from_fields` helpers in the store. Enums are stored as their `Display`/string names (or numeric for `Priority`) — route all conversions through these helpers rather than deserializing directly.
- `src/state.rs` — `ProjectState` is the client's read model for `scry list`: it groups a project snapshot into ordered section groups plus a trailing `No section` group, keeps closed tasks in a separate collection (rendered only by `--include-closed`), applies the project's sorting mode, and supports substring filtering. `get_task_by_id` and `tasks` are test-only helpers. It has no UI dependencies.
- The Postgres pool uses sqlx defaults, so concurrent writers are possible.

## Release process

- Version bumps are scripted in the justfile: `just release-patch|minor|major` (append `-and-push` to also push). The script edits the `Cargo.toml` version, runs `cargo check`, commits `Cargo.toml` and `Cargo.lock` as `vX.Y.Z`, and tags it.
- Pushing a `v*` tag triggers `.github/workflows/release.yml`, which cross-compiles and publishes `scry-<target>.tar.gz` tarballs; `install.sh` downloads exactly those artifact names.
- Keep the README CLI reference and `install.sh` in sync when adding/changing commands or flags.
