# AGENTS.md

`scry` is a terminal task manager with a PostgreSQL backend: a clap CLI. Rust edition 2024. It is a Cargo workspace: the root `scry` binary and `crates/scry-core` (domain types and the `Store` trait). The tests are unit tests that need no database; `just cargo-test` (alias `just test`) runs them (`cargo test --workspace`, with the default features, so `ui/dist` must exist). The `ui/` package is the React/TypeScript frontend (Vite, Flowbite React, oxlint, Prettier, Vitest, React Testing Library/jsdom); it is a separate npm package, not a Cargo workspace member.

## Tooling prerequisites

- The standard workflow uses `just` and sqlx-cli (`cargo install just sqlx-cli`). The `sqlx-prepare*` and `run-postgres` targets need sqlx-cli; the Postgres targets also need Docker, since they start and stop the Postgres defined in `compose.yaml`, which runs the app together with its own `postgres:18` service.
- `just run` (the `run-docker` alias) builds the web UI and release binary, builds the image, and starts the whole Docker stack, app plus database, so no host Postgres is needed; `just view-logs` tails the app container. `just run-local` builds the web UI and release binary and runs the REST server on the host against that same Postgres with `--config scry.dev.toml --secrets scry.dev-secrets.toml`, and `just run-postgres` only starts Postgres and applies migrations.
- `just pg-down` keeps the data volume and `just pg-reset` wipes it; `pg-reset` and `clean` take the whole stack down, and `clean` also runs `cargo clean` and removes `ui/dist`.
- The `ui/` package uses Node from `ui/.nvmrc` (Node 26). `just setup-ui-env` installs it through nvm and runs `npm install`; `just run-ui` starts the Docker stack and the Vite dev server on `:5173`; `just build-ui`, `just lint-ui`, `just prettier-check-ui`, `just typecheck-ui`, `just test-ui`, and `just prettier-fix-ui` are the UI build and check commands.
- The root crate has a default `embed-ui` feature that embeds `ui/dist` with `include_dir!`. `just build`, `install`, `run-local`, and `run` build the UI first; plain `cargo build`/`test`/`check`/`clippy` use the default features and therefore need `just build-ui` (or `just build`) to have produced `ui/dist`. `--no-default-features` builds an API-only binary with no embedded UI. CI uses `just cargo-test-ci`, `cargo-check-ci`, and `cargo-clippy-ci`, which pass `--no-default-features` and need no UI build.
- rust-analyzer is configured to run `cargo clippy` as its check command (`.vscode/settings.json`), and `just cargo-clippy` (alias `just clippy`) is `cargo clippy --workspace -- -D warnings`. Keep clippy clean at `-D warnings`. `just validate` is the local gate: it builds the UI, then runs Rust test/check/clippy with the default features, generated-binding and fixture drift checks, and UI lint/format/type-check/Vitest.

## sqlx compile-time database (the #1 gotcha)

All SQL lives in `sqlx::query!`/`query_as!` macros in `src/store/postgres.rs`, and is resolved at compile time against the committed offline cache in `.sqlx/`.

- `.env` (committed) sets only `SQLX_OFFLINE=true`. sqlx reads `.env` at compile time, so ordinary `cargo build`/`check`/`test`/`clippy` resolve queries from `.sqlx/` and do **not** need a live database. A fresh clone therefore compiles without any database.
- Regenerating the cache is what needs a database. `just run-postgres` starts the dev Postgres and applies the migrations, and `just sqlx-prepare` runs `sqlx-prepare-postgres`, which brings up the dev Postgres (`pg-up`), prepares against it, and tears it down.
- After editing SQL in a `query!` macro or adding a migration, run `just sqlx-prepare`. Changing a query changes its hash, so a stale `.sqlx/*.json` breaks the build. Commit the migration and the regenerated cache together.
- `just sqlx-prepare-check` verifies the cache is current, using the dev Postgres as well; CI runs it. Release CI (`.github/workflows/release.yml`) builds with `SQLX_OFFLINE=true` against the committed cache.
- The runtime database is **not** the compile DB. The app never reads `.env`; it takes `database_url` only from `scry.toml` or `scry.secret.toml` (or the files named by `--config` / `--secrets`), with no environment-variable override and no local-file fallback — a missing URL is a startup configuration error, and only `postgres://` / `postgresql://` URLs are accepted. `cargo run` therefore talks to whichever database the resolved config points at, so point `database_url` at a scratch database when you do not want to touch real user data. The backend is built with sqlx's `tls-rustls` feature (in the root `Cargo.toml`), so URLs whose `sslmode` requires TLS connect correctly; removing that feature breaks them with a "built without TLS support" error.

## Migrations

- `migrations/` holds the reversible `20261031164943_init` pair, which creates the sections/state schema with native uuid ids and `TEXT COLLATE "C"` positions from scratch and seeds the built-in default project with a fixed UUID, plus the `20261101062730_sync_state` pair that adds the sync storage tables (`applied_operations`, `changes`, `entity_tombstones`). There is no legacy migration path and no data migration from earlier builds: the init migration is applied from scratch, so a database created before the UUID rewrite or before the position conversion must be recreated or migrated manually. The snapshot file format is version 1 and any other version is rejected on import; there is no upgrade path. Add future migrations with `sqlx migrate add -r <name>`, filling in both files.
- Migrations are embedded (`sqlx::migrate!("./migrations")` in `src/store/postgres.rs`) and auto-run on **every app startup**. Databases created before the UUID rewrite or position conversion must be recreated; from this point on, new migrations must be additive/backward-compatible.
- The root crate has a `build.rs` that reruns when `migrations/` changes, so new migrations trigger a rebuild automatically.

## Architecture

- `src/main.rs` — clap command definitions and dispatch. Client commands go to `src/client/`; `serve` is the only database-backed path; `docs` and `skill` are local. With no subcommand it prints the top-level help.
- `src/client.rs` and `src/client/commands/**` — the HTTP client. `Client` (`src/client/http.rs`) builds URLs with `reqwest::Url`, sends the bearer token and `Time-Zone`, and maps server error documents into `AppError::Remote`. Each command has its own file, and `project_by_name`/`section_by_name` resolve names through the API. The client never opens the database.
- `src/output.rs` — shared `print_json`, `section_label`, and `task_line` rendering used by the client and the few local commands.
- `src/client_state.rs` — the client-local active project in `state.toml`; `set_active` persists a verified project name, and `project_by_name` falls back to `default` when it is stale.
- `src/service.rs` — `ProjectService` owns the store and is the only write path. Every REST mutation builds `Operation`s and applies them through `apply_operations(ops, ApplyMode::Atomic)`, which opens one transaction with `Store::begin_apply`, runs each operation through `apply_one_operation` (version check, `operation_id` dedupe, tombstone check, field application through the pure `task_field_updates`/`project_field_updates`/`section_field_updates`/`note_field_updates` helpers, store write, and one `changes` row per affected entity), and rolls the whole batch back on rejection so one HTTP write cannot leave partial state. The same function with `ApplyMode::PerOperation` is the per-operation entry point for `/sync` (#104): there a rejection is acknowledged without failing the batch. REST-produced operations carry `timestamp: None`, so `changes.client_timestamp` is NULL; `changes.created_at` is the server's required, informational timestamp (the server writes it), and `seq` remains the only ordering. Requests that create a section (`--new-section`, template seeding) or merge sections emit several operations in the same atomic batch, so they can no longer leave partial state. Idempotency keys are not implemented; #115 tracks the optional follow-up. It is the operations layer: it resolves section names to ids (exact match; an absent name fails), resolves task and note handles to UUIDs (failing on ambiguity with longer candidates), creates sections only when explicitly asked (`--new-section` or `section add`), merges sections by moving their tasks to the target in one batch, generates lexicographic position keys for new tasks and sections (new rows append), and mutates tasks by reading the row and building `UpdateTask`/`MoveTask` operations for exactly the fields the patch names — so concurrent edits to different fields are last-write-wins. Reordering is not exposed: task moves always append, and sections cannot be reordered. Projects and sections remain name-based; tasks and notes accept id handles. Every server mutation, including import, goes through it: `import` opens one `begin_apply` transaction, loads live rows and referenced tombstones through the store inside that transaction, calls the pure `scry_core::snapshot::plan_import`, and applies the resulting operations with `ApplyMode::Atomic` before committing; reads may use `Store` directly. The REST `ScryState` holds the service, and the client reaches it over HTTP.
- `src/server/` — the REST router and one handler per endpoint. Detailed responses use `TaskDetails` (flattened task plus optional `notes` and `handle`) and the project detail response (flattened project plus `sections` and `tasks`). `POST /api/v1/sync` applies a pushed batch with `ApplyMode::PerOperation`, then returns every `changes` row after `last_seen_seq` as resulting field values plus `next_seq`; `GET /api/v1/max_seq` returns the highest `seq`; `GET /api/v1/snapshot` returns the bare `{ projects, last_seen_seq }` document; and `GET /api/v1/export?include_seq=true` adds the cursor to the importable `SnapshotFile`. The `SyncRequest`/`SyncResponse` handler types live in `src/server/handlers/sync.rs`, and `ChangeEntry` is in `crates/scry-core/src/models.rs`. The same module embeds the built web UI behind the default `embed-ui` feature and serves it from a fallback in `src/server/router.rs`: a request path is resolved against `ui/dist`, and anything else returns `index.html` for client-side routing. The `/api/v1` router keeps its own 404 fallback so unmatched API paths never reach the UI. The optional auth gate wraps only the API resources and accepts a bearer token or the signed `scry_session` cookie; `src/server/auth.rs` holds the ungated `GET`/`POST`/`DELETE /api/v1/auth/session` endpoints. The embedded assets are served with `application/manifest+json` for `webmanifest`; `index.html`, `sw.js`, `registerSW.js`, the manifest, and icons get `no-cache`, while hashed `assets/*` get a one-year immutable cache. Those explicit headers go beyond luxide's content-type-only serving so a new binary cannot strand cached HTML against deleted hashed assets.
- `ui/vite.config.ts` — `vite-plugin-pwa` (`generateSW`, `autoUpdate`) precaches the app shell with `/index.html` as the navigation fallback, denies `/api/` and `/sync` navigations, cleans outdated caches, and disables the worker in dev. The manifest is defined in `ui/vite.config.ts` and emitted at build time; the generated 192/512/maskable/apple-touch icons live in `ui/public/`; `ui/index.html` carries the theme colour and Apple install metadata.
- `ui/src/utils/replica/` — the local Replica: one `scry-replica` IndexedDB database with UUID-keyed `projects`/`sections`/`tasks`/`notes` stores, a FIFO `outbox` keyed by auto-increment `seq`, and `meta` for schema version, bootstrap flag, and order arrays. It reuses `ui/src/contract/op-replay.ts` for confirmed/visible state, persists confirmed state in one transaction, preserves the outbox across confirmed-schema wipes, requests storage persistence, persists the sync cursor (`lastSeenSeq`/`setLastSeenSeq`), reloads from IndexedDB for cross-tab fan-out, and maps quota failures to tagged `ReplicaError`s. Luxide has no local replica/outbox analogue; React bindings are #125.
- `ui/src/utils/sync/` — the non-React sync client. `createSyncClient` bootstraps from `GET /api/v1/snapshot` when `replica.needsBootstrap`, pushes the outbox to `POST /api/v1/sync`, applies returned changes, advances the Replica cursor, acknowledges applied and ordinary rejected operations, keeps `unsupported_version` operations queued, and exposes `status`, `error`, `rejected`, `getSnapshot`, and `subscribe`. Requests live in `ui/src/utils/api.ts`; scheduling and retry live in `ui/src/hooks/useSyncTriggers.ts`.
- `ui/src/providers/Sync/` and `ui/src/hooks/useSyncTriggers.ts` — the React sync layer. `SyncProvider` creates one sync client per ready Replica, runs startup/edit-debounce/visibility/online/manual triggers, and exposes `useSync`/`useSyncSnapshot`; `SyncButton` reports syncing and failure and calls `syncNow`. Triggers require an authenticated leader; followers and signed-out tabs disable the button and run no triggers; the leader reloads before syncing and broadcasts when a sync attempt finishes. Triggers use configurable `SyncTiming` defaults, poll only while visible, retry network/server/storage failures with exponential backoff, and skip auto-retry on 401 or `unsupported_version`. Startup is guarded once per client across StrictMode remounts.
- `ui/src/hooks/useSyncLeadership.ts` — one sync leader per origin through an exclusive `scry-sync-leader` Web Lock held for the tab's lifetime. The leader broadcasts `replica-updated` after sync attempts and followers broadcast `outbox-changed` when they queue edits; `scry-sync` BroadcastChannel messages are hints only, and every receiver reloads the shared IndexedDB Replica. Leadership transfers through the lock queue when the leader unmounts or closes. If Web Locks or BroadcastChannel is unavailable, every tab leads to preserve correctness at the cost of duplicate requests; the server dedupes operation ids and replay is idempotent.
- `ui/src/providers/Replica/` — React binding for the local Replica. `ReplicaProvider` opens it once, exposes loading/error/ready with retry, and closes it on unmount; `useReplica` guards ready consumers, and `useReplicaSnapshot` is a thin `useSyncExternalStore(replica.subscribe, replica.getSnapshot)`. `useReplicaStatus` is for shell state. Luxide has no `useSyncExternalStore` analogue.
- `ui/src/providers/ActiveProject/` — active-project context. The selected UUID persists in `localStorage` under `scry.activeProjectId` through `ui/src/utils/activeProject.ts`; the provider derives the active id from the current `/projects/:projectId` route and the stored id, falling back to the first visible project.
- `ui/src/providers/Auth/` — SPA auth following luxide's provider shape. `AuthProvider` probes `GET /api/v1/auth/session` with credentials, exposes `isAuthenticated`/`isAuthLoading`/`login`/`logout`, and never stores the token. `ui/src/utils/api.ts` sends the token only in the login body; `ui/src/utils/authEvents.ts` carries 401s from normal API helpers to the provider. A `scry-auth` BroadcastChannel broadcasts `signed-in`/`signed-out`, so login, logout, and 401s converge every open tab.
- `ui/src/views/` — the route skeleton: public `/login` token form, plus the guarded project list, `/projects/:projectId` board placeholder, nested task placeholder, and settings. Dynamic views use luxide's `[param]` folder convention.
- `ui/src/hooks/useOnlineStatus.ts` — `navigator.onLine` through `useSyncExternalStore` with `online`/`offline` listeners.
- `src/http_auth.rs` — shared API credentials. `AuthState` derives the cookie signing key from SHA-256 of `api_token`, so rotating the token invalidates sessions; the gate accepts a bearer token or a signed `scry_session` cookie. The cookie is `HttpOnly`, `SameSite=Strict`, `Path=/`, expires after 30 days, and gains `Secure` from `X-Forwarded-Proto: https`. With no token, auth is disabled; session creation returns 400 and clearing succeeds. CORS remains wildcard without credentials.
- `crates/scry-core/src/ids.rs` — UUID id aliases (`ProjectId`, `SectionId`, `TaskId`, `NoteId` are `Uuid`) and the short-handle utilities (`Handle` parsing and range bounds, `shortest_handle`/`shortest_handles`). Rust generates every id: v4 for new entities and v5 for template sections, derived from the project UUID plus the section name; the database has no id defaults.
- `crates/scry-core/src/store.rs` — `Store` async trait declaring every DB operation. One implementor: `PostgresStore` (`src/store/postgres.rs`). All `query!` calls live there. Postgres stores ids as native `uuid` columns; task and note handles resolve with a padded `BETWEEN` range query over all rows (closed tasks included, across projects), while projects and sections stay name-based. Every method takes a final `tx: Option<&mut PgConnection>`: `None` runs on a pooled connection, `Some` runs inside the caller's transaction and the caller owns the commit. It covers task CRUD plus a single `update_task` that writes the whole row; section CRUD plus `delete_section` (tasks fall back to No section); there is no section reorder operation; note and project CRUD; the project document snapshot read used by the snapshot endpoint and export; `begin_apply`, which returns the batch transaction after taking an advisory lock; and the sync primitives `is_operation_applied`, `record_applied_operation`, `is_tombstoned`, `create_tombstone`, `record_change`, `changes_after` and `last_change_seq`. Creates take completed models, so the service fills every column and the database has no usable defaults. Add new persistence via the trait plus the implementor.
- `crates/scry-core/src/models.rs` — domain types (`Task`, `Project`, `Section`, `TaskState`, `Priority`, …). A task has a nullable `section_id`, a `Position` string key, and a `state` of `Open` or `Closed`. Positions use the default Rocicorp fractional-index format and sort lexicographically; every ordering breaks ties by `(position, id)`. `TaskSortingMode::Created` sorts by `(created_at, id)`, with `id` kept as a CLI alias for compatibility. `ProjectSnapshot` is the canonical project document — the project's own fields flattened into the object's top level alongside `sections`, `tasks`, and `notes` — returned by `GET /projects/{id}/snapshot` and used as each snapshot file entry. `crates/scry-core/src/snapshot.rs` defines `Snapshot` (projects plus cursor) and `SnapshotFile` (the versioned import/export envelope: `version`, `app_version`, `projects: Vec<ProjectSnapshot>`, optional `last_seen_seq`); the format is version 1 and any other version is rejected on import; `SnapshotFile.last_seen_seq` is an optional sync cursor that ordinary exports omit. It also defines the pure `plan_import` planner (`ImportState` plus `SnapshotFile` to operations plus an import report), so import reuses the normal operation pipeline. `src/config.rs` handles config, server URL, and DB URL resolution, and `src/skill.rs` implements the embedded Agent Skill command.
- `crates/scry-core/src/position.rs` — the vendored default-format Rocicorp fractional-index algorithm (CC0), plus the `Position` newtype, validation, `key_between`, and `n_keys_between`. Keys look like `a0`, `a1V`, and `Zz`. `PostgresStore` stores them as `TEXT COLLATE "C"` so database and Rust ordering agree byte-for-byte.
- `crates/scry-core/src/ordering.rs` — the shared task-ordering rule: `compare_tasks` orders by `TaskSortingMode` and breaks every tie by id. Both `src/state.rs` and `ui/src/contract/task-order.ts` use it. Closed tasks follow the same rule; the closed filter controls visibility, not order.
- Row->model mapping is hand-rolled per query via the `*_from_fields` helpers in the store. Enums are stored as their `Display`/string names (or numeric for `Priority`) — route all conversions through these helpers rather than deserializing directly.
- `src/state.rs` — `ProjectState` is the client's read model for `scry list`: it groups a project snapshot into ordered section groups plus a trailing `No section` group, keeps closed tasks in a separate collection (rendered only by `--include-closed`), orders every task with `scry_core::ordering::compare_tasks`, and supports substring filtering. `get_task_by_id` and `tasks` are test-only helpers. It has no UI dependencies.
- The Postgres pool uses sqlx defaults, so concurrent writers are possible.

## Cross-language contract

The Rust server and the TypeScript UI must agree on the wire format and on every rule implemented in both languages.

- Wire types in `crates/scry-core` derive `ts_rs::TS` behind the optional `ts` feature; the root `SyncRequest`/`SyncResponse` do the same. `just generate-bindings` runs the exporter and writes `ui/src/generated/`; `just check-bindings` regenerates and fails on a diff. `ui/src/generated/` is machine-owned: never hand-edit or hand-add types there. Put hand-written client types outside it.
- Every rule implemented in both languages gets a fixture area under `fixtures/<area>/cases.json`. The envelope is versioned (`version`, `area`, optional `description`, `cases`); each case has `name`, optional `description`, `kind`, `input`, and `expected`. Unknown fields and unsupported versions are rejected. `input` and `expected` are always JSON objects.
- The Rust loader is `crates/scry-core/tests/common.rs`; the TypeScript loader is `ui/src/fixtures/load.ts`. Both keep the same `REGISTERED_AREAS`. A fixture directory missing from either registry, a registered area without `cases.json`, or a case `kind` that an area test does not consume fails the suite.
- `just generate-fixtures` rewrites the committed fixtures from Rust; `just check-fixtures` regenerates and fails on a diff. Adding a dual-language rule means adding the area, registering it in both loaders, and consuming every case on both sides in the same change.
- Fixture versions start at `1`. Bump `version` only for an incompatible schema or semantic change; additive cases do not bump it. Consumers reject any other version, and there is no upgrade path.
- `crates/scry-core/src/sync/replay.rs` is the reference client model: confirmed state, applying pulled changes, replaying the unacknowledged outbox, and computing visible state. The server never calls it. The fixture generator, `crates/scry-core/tests/op_replay.rs`, and the TypeScript mirror in `ui/src/contract/op-replay.ts` use it to pin the client-side rule.
- Current areas are `positions` (`position.rs` / `ui/src/contract/positions.ts`), `handles` (`ids.rs` / `ui/src/contract/handles.ts`), `op-replay` (`sync/replay.rs` / `ui/src/contract/op-replay.ts`), and `task-order` (`ordering.rs` / `ui/src/contract/task-order.ts`).
- CI (`.github/workflows/ci.yml`, currently manual `workflow_dispatch` only) runs the binding and fixture drift checks, the Rust gates, UI lint/format/type-check, and Vitest.

## Release process

- Version bumps are scripted in the justfile: `just release-patch|minor|major` (append `-and-push` to also push). The script edits the `Cargo.toml` version, runs `cargo check --no-default-features`, commits `Cargo.toml` and `Cargo.lock` as `vX.Y.Z`, and tags it.
- Pushing a `v*` tag triggers `.github/workflows/release.yml`, which builds `ui/dist`, cross-compiles and publishes `scry-<target>.tar.gz` tarballs with the UI embedded; `install.sh` downloads exactly those artifact names. The Docker image is built from the prebuilt `x86_64-unknown-linux-gnu` artifact, and the Dockerfile is runtime-only: it copies `target/release/scry`, so `just run` builds it first.
- Keep the README CLI reference and `install.sh` in sync when adding/changing commands or flags.
